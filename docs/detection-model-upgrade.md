# 객체 검출 모델 교체 기록

실증 평가에서 객체 인식 성능 저하가 지적되어 일반 객체 모델을 Objects365 YOLO26n(640)에서 COCO 사전학습 YOLO26l(736×1280 고정 입력)로 교체하였다. 후처리를 벡터화하여 큰 모델의 추가 연산을 상쇄하였다. 2026-10-19 운영 분석 서버에 적용하였다.

## 원인

2026-10-16 실증 사진과 2026-10-19 운영 원본 프레임에서 원거리 보행자, 유모차를 미는 사람, 작업자를 놓치고 자전거를 `person`으로 판정하는 사례가 확인되었다. 원인은 다음과 같다.

| 원인 | 내용 |
|---|---|
| 모델 용량 | 운영 모델이 파라미터 약 280만 개의 nano 모델이다. |
| 입력 해상도 | 1280×720 프레임을 640으로 축소하여 소형 인물의 높이가 절반이 된다. |
| 후처리 비용 | 원시 출력의 앵커를 Python 루프로 순회하여 1280 입력에서 약 18ms, 이동수단 모델에서 약 7.5ms를 소비하였다. 이 비용 때문에 큰 모델을 적용하지 못하였다. |
| 사람→자전거 보정 | nano 모델용 보정 규칙이 새 모델에서는 실제 보행자·자전거 탑승자를 `bicycle`로 변경하였다. |
| 휠체어 오검출 | 이동수단 모델이 테스트핀3 화면 우측 하단에 프레임 면적 24~33%의 `wheelchair` 박스를 반복 출력하였다. 운영 로그의 휠체어 202건 다수가 이에 해당하는 것으로 판단한다. |

## 변경 내용

| 항목 | 변경 |
|---|---|
| 주 모델 | `result/models/coco_yolo26l_736x1280.onnx`. 정확도 중심 one-to-many 헤드, FP32, opset 17 |
| 후처리 | 원시 출력의 class 선택·임계값·좌표 복원을 numpy 연산으로 처리한다. 결과는 기존 루프와 같다. |
| 사람→자전거 보정 | `OBJECT_PERSON_RELABEL`로 선택한다. 미설정 시 기존 동작(`1`)을 유지하고, Dockerfile은 YOLO26l과 함께 `0`을 지정한다. 이전 자전거 위치의 현재 프레임 재검출(`ROI_REDETECTION`)은 설정과 관계없이 유지한다. |
| 이동수단 박스 | 프레임 면적 20% 초과 박스를 제외한다. |
| 킥보드 중복 | COCO에는 킥보드 class가 없어 킥보드를 `bicycle`로 판정한다. 이동수단 모델의 `scooter`와 IoU 0.5 이상 겹치는 주 모델 `bicycle`·`motorcycle`을 제거한다. |
| 내보내기 도구 | `export_yolo26.py --imgsz 736 1280`으로 직사각형 고정 입력을 생성한다. |

`raw.method`의 `objects365_yolo26n+mobility_yolov8s` 문자열은 백엔드가 객체 분석 수행 여부를 판정하는 식별자이므로 변경하지 않았다. 응답 필드와 구역·트램·경보 정책은 변경하지 않았다.

```bash
python export_yolo26.py result/models/coco_yolo26l.pt \
  result/models/coco_yolo26l_736x1280.onnx --imgsz 736 1280
```

## 속도

운영 기준은 카메라 8대, 카메라별 약 0.5초 간격(전체 약 11.7건/초), 단일 분석 워커이다. 2026-10-16 분석로그의 촬영~완료 지연은 p50 540ms, p95 881ms였고 구간별 증가는 없었다. 운영 컨테이너 로그의 건당 분석 시간은 p50 34.1ms, p95 37.0ms이다.

`YoloDnnDetector.detect()` 전체(전처리, 주 모델, 이동수단 모델, 후처리, 구역 판정)를 GPU1의 ONNX Runtime 1.23.2 CUDA 실행으로 측정하였다. 운영 Docker 이미지에는 TensorRT가 없으므로 CUDA 실행만 기준으로 사용하였다. GPU1은 다른 프로세스와 공유 중이었다.

| 구성 (같은 운영 프레임 120장) | p50 | p95 |
|---|---:|---:|
| 기존 코드 + Objects365 YOLO26n 640 (현재 운영) | 43.5ms | 70.2ms |
| 새 코드 + COCO YOLO26l 736×1280 (적용안) | 24.5ms | 29.8ms |

측정 중 GPU1은 다른 프로세스로 사용률 62~64%였다. 운영 GPU0에서는 객체 검출을 포함한 건당 전체 분석이 34ms이므로, 위 수치는 절대 지연이 아니라 같은 GPU에서의 상대 비교로 사용한다. 다른 후보의 기존 코드 기준 측정값은 `result/detection-upgrade/speed.jsonl`, 벡터화 후 측정값은 `speed2.jsonl`·`speed3.jsonl`에 기록하였다. 객체 검출 단계가 기존보다 짧아졌으므로 건당 분석 시간은 현재 운영값을 넘지 않을 것으로 판단한다. 운영 GPU0에서 얼굴·군중 모델과 함께 실행한 전체 지연은 교체 후 확인한다.

## 정확도

### 평가 방법

`/upload/visit_servant/analyzed`의 프레임에는 박스가 그려져 있어 사용하지 않았다. 2026-10-19 08:52~09:05에 `/upload/visit_servant/frames`에서 8대 카메라의 원본 프레임을 약 5초 간격으로 수집하였다.

사람 정답 라벨이 없어 YOLO26x와 YOLO11x를 1920 입력으로 실행하고, 두 모델이 같은 class·IoU 0.5 이상으로 합의한 박스(한쪽 신뢰도 0.4 이상, 다른 쪽 0.25 이상)를 기준으로 사용하였다. 후보 결과는 운영 경로인 `YoloDnnDetector.detect()`의 출력이다.

- 재현율: 기준 박스와 같은 class·IoU 0.5 이상으로 일치한 비율
- 소형 인물: 기준 박스 높이 48px 미만인 `person`
- 오분류: 기준 박스와 IoU 0.5 이상이나 다른 class로만 검출한 수
- 근거 없음: 두 기준 모델의 신뢰도 0.15 이상 박스와 같은 class·IoU 0.3 이상으로 겹치지 않는 출력

모델 선정은 347장(선정 세트)으로 수행하고, 이후 수집한 826장(검증 세트)으로 결과를 확인하였다.

### 쓰러짐 판정

기존 쓰러짐 재생 검증(`docs/replay-fall-validation.py`, `test_video.mkv` 4 FPS)을 두 모델로 실행하였다. 사람 출력은 1,788건에서 4,039건으로, 고유 추적 ID는 88개에서 71개로 변하였다. 두 모델 모두 쓰러짐 이벤트는 0건이며 모든 사람의 상태가 `UNKNOWN`이었다. 쓰러짐 신호를 위험 경보 조건으로 제한한 이후 이 재생에는 구역·트램 입력이 없어 쓰러짐 판정이 수행되지 않는다. 새 모델의 박스 형태에 대한 쓰러짐 판정 재검증은 미실시 상태이다.

### 해석 범위

기준 박스는 사람 라벨이 아닌 대형 모델의 합의 결과이다. 기준 모델 중 하나가 YOLO26 계열이므로 YOLO26 후보에 유리할 수 있다. 수치는 모델 간 상대 비교로 사용하고 절대 정확도로 보고하지 않는다.

평가 프레임은 평일 오전 약 13분 구간이며 야간·우천·혼잡 시간대를 포함하지 않는다. 동물 4건, 오토바이 1건으로 해당 class는 판단할 수 없다. 근거 없음 박스의 상당수는 자전거 탑승자 전체를 하나의 `bicycle`로 표시한 경우이고, 실제 오검출로는 파라솔·천막 하부를 `person`으로 판정한 사례가 확인되었다(`l35_fp.jpg`).

남은 누락의 대부분은 거치대에 겹쳐 세운 자전거와 원거리 인물이다(`l35_miss.jpg`). YOLO26x 1920 입력에서도 거치 자전거 점수가 0.1~0.4에 머물러 모델 크기로는 개선이 제한된다. 해당 누락을 줄이려면 운영 카메라 원본 프레임에 라벨을 부여하여 미세조정해야 한다.

## 운영 적용

운영 컨테이너는 저장소를 `/app`으로 마운트하므로 코드 변경은 재시작 시 반영된다. 모델 경로는 컨테이너 환경변수로 지정되어 있으므로 다음 두 값을 함께 변경한다. 환경변수를 바꾸지 않고 재시작하면 기존 nano 모델과 기존 사람→자전거 보정이 유지되고, 후처리 벡터화·이동수단 박스 크기 제한·킥보드 중복 제거만 반영된다.

```bash
OBJECT_MODEL_PATH=/app/result/models/coco_yolo26l_736x1280.onnx
OBJECT_PERSON_RELABEL=0
```

적용 후 컨테이너 로그의 `analysis done ... ms=` 값과 백엔드 분석로그의 촬영~완료 지연이 현재 수준(건당 p50 약 34ms, 지연 p50 약 540ms)을 유지하는지 확인한다.

### 적용 결과

2026-10-19 09:27(KST)에 `/app/visit_servant_api/compose.yaml`의 `analysis` 환경변수를 위 값으로 변경하고 `docker compose up -d --no-deps --no-build analysis`로 재생성하였다. 원본은 `compose.yaml.bak-20261019-detector`에 보관하였다. 적용 직전 같은 이미지의 임시 컨테이너(GPU1)에서 ONNX Runtime 1.23.2 CUDA 로딩과 검출 시간 p50 26.1ms·p95 28.7ms를 확인하였다.

적용 후 86초간 908건(약 10.5건/초)을 오류 없이 처리하였다. 건당 분석 시간은 p50 38.6ms, p95 43.2ms(최근 400건, 시작 직후 초기화 3건 제외)로 적용 전 p50 34.1ms, p95 37.0ms보다 약 4~6ms 증가하였다. 단일 워커 사용률은 약 41%로 대기열 증가는 없다. 건당 객체 수는 1.08개에서 7.77개로 증가하였으나 적용 전 로그는 08시대 저통행 구간이므로 직접 비교하지 않는다.

미세조정 모델은 임계값 부근의 주차 자전거를 간헐적으로 검출한다. 이때 추적 ID가 바뀌며 `ENTER`가 반복되어(테스트핀6 펜스 옆 자전거 15분간 127건) 정지 객체에 대해 다음을 추가하였다.

- 사라진 트랙의 ID·구역 상태를 60초 동안 보관하고, 같은 class가 같은 위치에 다시 검출되면 이어받는다. 이동하던 트랙은 이어받지 않는다.
- 같은 위치에 머문 객체는 구역 하향을 60초 연속일 때만 반영한다. 경계에 걸쳐 대부분 밖에 있다가 가끔 안으로 판정되는 주차 자전거의 `ENTER`·`EXIT` 반복을 막는다.
