# 핵심 성능 평가

## 측정 범위

`evaluate_kpi.py`는 이벤트 정답(GT), 검토 완료 구간, 실제 경보, 표출시각, BEV 갱신시각, 반복 좌표 측정을 각각의 평가 산식에 적용한다. 입력이 없는 항목은 미측정으로 표시한다. 시간은 동일 시간대의 `YYYY-MM-DD HH:MM:SS.fff` 형식이며, 카메라 식별자는 엑셀의 `카메라ID`와 일치해야 한다.

| 데이터 | 평가 항목 | 산식 및 기준 |
|---|---|---|
| 위험 이벤트 GT + 실제 경보 | 위험 시나리오 경보 일치율 | TP / 검토 완료 위험 시나리오 수. 비위험 창을 추가하여 일치율을 높이지 않는다. |
| 위험 이벤트 GT + 실제 경보 | Precision / Recall / F1 | TP/(TP+FP), TP/(TP+FN), 2TP/(2TP+FP+FN) |
| 검토 완료 구간 + 위험 이벤트 GT + 실제 경보 | FPR | 경보가 있는 비위험 창 / 전체 비위험 창. 검토 시간당 오경보 건수도 병기한다. |
| 가림 진입 GT + 실제 경보 | 비가시권 위험 포착률 | 진입 전 지정 시간 내 경보가 있는 진입 이벤트 / 전체 검토 완료 진입 이벤트 |
| GT + 실제 경보 + 화면 표출 기록 | E2E 반응성 | 이벤트 시작 → 연결된 경보의 최초 화면 표출. 관제와 글래스 채널별 평균·P95 |
| 촬영·BEV 갱신시각 | BEV 갱신 지연 | 동일 프레임의 BEV 갱신시각 − 촬영시각. 평균·P95 |
| GT·측정 좌표 | 좌표 정확도 | 반복 측정별 2차원 유클리드 오차의 RMSE·P95, 단위 cm |
| 분석 엑셀 | 보조 운영 지표 | 촬영 → 분석완료 지연 및 카메라별 촬영 간격(서로 다른 export 사이의 공백 제외). BEV·E2E 목표 판정에 사용하지 않는다. |

위험 시나리오 경보 일치율은 위험 시나리오만을 분모로 하는 구현 기준이다. 비위험 시나리오를 포함하는 별도 시험 규약이 있는 경우 해당 규약과 정합성 확인이 필요하다. 1차년도 목표값은 코드의 `TARGETS`에 정의되어 있다.

## 입력 파일

[합성 입력 예제](../examples/kpi/)는 형식 확인과 회귀 테스트용이며 현장 성능의 근거가 아니다.

| 파일·옵션 | 필수 열 | 입력 기준 |
|---|---|---|
| 분석 엑셀, 위치 인자 | `분석로그`, `검출객체` 시트 | 기존 분석 export 형식. 여러 파일의 동일 카메라·로그는 중복 제외 |
| `--gt` | `camera_id,start,end,scenario` | `scenario`는 `normal` 또는 `occluded`. 선택 열 `class`, `track_id`로 대상 제한 |
| `--coverage` | `camera_id,start,end` | 사람이 위험·비위험을 모두 검토한 구간. 단순 촬영 구간을 입력하지 않는다. |
| `--alerts` | `camera_id,time,track_id,class` | 실제 최종 발행 경보의 이벤트 발생시각. 선택 열 `completed_at`은 해당 분석 완료시각 |
| `--display` | `camera_id,track_id,displayed_at,channel` | 실제 화면 표출시각. `control`은 관제, `glasses`는 스마트글래스 |
| `--bev` | `camera_id,frame_id,captured_at,updated_at` | 동일 프레임의 원본 촬영시각과 BEV 결과 갱신 완료시각 |
| `--coords` | `point_id,trial,gt_x_cm,gt_y_cm,meas_x_cm,meas_y_cm` | 측량 기준 좌표와 동일 좌표계의 반복 측정. 같은 지점을 여러 회 측정 |

`--alerts`가 없으면 엑셀 `검출객체`의 `ENTER/ESCALATE`를 구역 전이 후보로 평가한다. 해당 기록에는 트램 접근에 따른 최종 경보 여부가 없으므로 시스템 경보 평가로 보고하지 않는다. JSON의 `settings.evaluation_scope`에도 이 구분을 기록한다. `위험알람` 시트는 체류 기록 등이 포함되어 경보 시작과 일대일 대응하지 않으므로 자동 대체하지 않는다.

`--event-type fall`은 `쓰러짐이벤트=ENTER`를 선택하여 구역 `STAY` 중 발생한 새 쓰러짐도 집계한다. 유형별 GT·실제 경보 CSV를 구분하여 사용한다. 원본 입력 보존과 기존 모델 후보의 실험 결과는 [기존 시스템 기반 KPI 개선 조사](kpi-candidate-investigation.md)를 참조한다.

원본과 DB 결과를 연결한 검토 자료 준비, 후보 CSV와 최종 경보 CSV의 구분, 부분 실패 계측은 [위험 이벤트 평가 및 부분 실패 계측](event-evaluation-workflow.md)을 참조한다.

GT는 사람이 검토한 실제 위험 시나리오를 기준으로 작성한다. 모델 출력·기존 경보를 그대로 정답으로 복사하지 않는다. `track_id`는 실제 경보와 대상 연결을 검토한 경우에만 지정한다. `--classes` 적용 시 모든 GT 행에 `class`가 필요하며 양쪽 입력에 같은 클래스 필터를 적용한다.

## 이벤트 판정 규칙

- 일반 이벤트의 매칭 범위는 `[start − tolerance, end + tolerance]`이다. 기본 허용 오차는 2초이다.
- 비가시권 이벤트의 `start`는 가림 진입시각이다. `[start − occluded_lead, start]`의 경보만 사전 포착으로 인정한다. 기본 사전 포착 범위는 5초이다.
- 카메라와 지정한 클래스·트랙이 일치해야 한다. 겹치는 이벤트는 일대일 최대 매칭을 적용하며, 같은 이벤트의 추가 경보는 중복으로 별도 집계한다. 중복 경보는 FP에 추가하지 않는다.
- GT 시작과 끝이 하나의 검토 완료 구간에 모두 포함된 이벤트만 분모에 포함한다. 일부만 포함된 이벤트는 제외하며, 해당 위험 시간도 비위험 분모에서 제외한다.
- 중첩·인접 검토 구간은 합친다. 위험 구간과 허용 오차를 제거한 각 비위험 구간을 `--window` 단위로 분할한다. 기본 창 길이는 10초이고 마지막 짧은 창도 한 개로 센다. 내부 창 경계의 경보는 다음 창에 한 번만 포함한다.
- FP는 어떤 GT에도 연결되지 않은 경보 건수이다. FPR은 비위험 창의 비율이므로 FP 건수와 분모가 다르다. 분모가 0인 지표는 `null`로 출력한다.

창 길이·허용 오차·사전 포착 범위는 평가표에서 수치가 지정되지 않은 구현 기본값이다. 공식 평가 전에 확정하고 비교 시험에서는 동일하게 유지한다.

## 시간 및 계측 조건

모든 장비의 시계를 동기화한 뒤 측정한다. `--time-offset`은 GT·coverage·display 시각에만 더하는 초 단위 보정값이다. 경보와 BEV 시각은 export의 기준 시계를 사용한다.

E2E는 매칭된 트랙의 경보 발생 이후 첫 표출을 연결한다. 동일 트랙에 다음 매칭 이벤트가 있으면 그 경보 이후의 표출을 이전 이벤트에 재사용하지 않는다. 사전 경보가 진입 전에 표출된 경우 진입 기준 지연은 0초로 계산한다. GT 시작→분석완료의 부호 있는 시간차는 별도 보조 지표로 남긴다. 트랙 ID가 재시작·재사용되는 세션은 파일을 나누어 평가한다.

`matched_without_display`는 경보는 매칭되었으나 표출 기록이 없는 수, `unmatched_gt_events`는 경보가 매칭되지 않은 GT 수이다. `complete=false`이면 일부 성공 표본의 평균·P95만 산출된 상태이다. 누락이 있으면 목표 판정은 미측정으로 표시한다. 두 채널 모두 누락 여부를 확인해야 한다.

평가 도구의 CSV 입력은 구현됨 상태이다. 외부 백엔드의 최종 경보, 관제·글래스 표출, BEV 갱신 시점의 실제 기록 수집은 별도 연동 대상이며 현재 엑셀만으로 복원할 수 없다.

## 실행 예시

실제 엑셀의 분석 지연과 구역 전이 후보 수 집계:

```bash
mkdir -p result
python evaluate_kpi.py analysis-export_2026-10-21T153540_2026-10-21T153630/*.xlsx \
  --output result/kpi-export.json
```

합성 입력의 모든 평가 경로 확인:

```bash
mkdir -p result
python evaluate_kpi.py \
  --gt examples/kpi/gt.csv --coverage examples/kpi/coverage.csv \
  --alerts examples/kpi/alerts.csv --display examples/kpi/display.csv \
  --bev examples/kpi/bev.csv --coords examples/kpi/coords.csv \
  --tolerance 0 --output result/kpi-example.json
pytest -q test_evaluate_kpi.py
```

예제의 예상 결과는 TP 2건, FP 1건, FN 0건, Precision 2/3, Recall 1, F1 0.8이다. BEV 평균은 250ms이며 분석 지연은 입력 부재로 미측정이다. 현장 데이터 평가 시에는 예제 CSV를 검토 완료된 실측 입력으로 교체한다.

## 2026-10-27 실측 결과

운영 구간은 KST 12:17:00~12:18:00이며 카메라 8대의 분석 로그 748건을 조회하였다. `COMPLETED` 747건과 `TIMEOUT` 1건(`fetch failed`)을 확인하였다. 완료 표본만의 지연과 전체 상태별 건수를 구분하여 집계하였다.

| 측정 구간 | 표본 수 | 평균 | P95 |
|---|---:|---:|---:|
| 운영 촬영 → 분석완료 | 747 | 1,006.5ms | 1,399.7ms |
| 운영 촬영 → 분석 요청 로그 생성 | 747 | 485.5ms | 802.0ms |
| 운영 분석 요청 로그 생성 → 분석완료 | 747 | 521.0ms | 635.7ms |
| 저장 사진 재생 입력 예정시각 → 결과 직렬화 | 748 | 95.6ms | 170.8ms |
| 저장 사진 재생 대기열 | 748 | 39.1ms | 115.7ms |
| 저장 사진 재생 작업 시작 → 결과 직렬화 | 748 | 56.4ms | 63.5ms |

재생은 운영과 동일한 모델 4개(DM-Count, FT3 YOLO26l, 이동수단 YOLOv8s, SCRFD)를 RTX 4090 GPU1의 별도 컨테이너에서 실행하였다. 운영 GPU0의 서비스 요청이나 DB에는 재생 결과를 전송하지 않았다. `measure_analysis.py`는 원래 촬영 간격으로 프레임을 공급하고 실제 분석 worker의 대기열·직렬화까지 측정한다. 입력 748건 중 실패·결과 누락은 0건이며 최대 대기열은 4건, 마지막 입력 이후 잔여 처리시간은 0.151초였다. 59.906초의 기록을 60.057초에 처리한 실측 처리율은 전체 카메라 합산 12.455 FPS이다. 이는 기록된 입력률에 대한 처리 결과이며 최대 처리 성능이나 카메라당 4 FPS를 의미하지 않는다.

재생 입력은 검출 박스가 포함된 export 분석 사진이다. 저장 사진의 재생 결과는 처리 경로·지연 검증에 사용하며 원본 영상의 검출 정확도나 실제 관제·글래스 표출 E2E로 보고하지 않는다. 운영 촬영시각도 저장 파일명에서 취득한 기록이므로 센서 노출시각부터의 지연은 확인 필요이다. 위 두 지연은 서로 다른 구간이며 BEV 지연을 대신하지 않는다.

2026-10-23 09:28:39~09:34:00의 실제 경보 75건도 확인하였다. 기존 대시보드는 실제 기기 발성시각이 없으면 초 단위 `riskDate`를 대체 사용하여 평균 −0.193초를 반환하였다. 백엔드 `kpi.service.ts`에서 대체값을 제거하고 음수 시간차를 표본에서 제외하였다. 수정 후 같은 API 구간은 `sampleCount=0`, `averageSeconds=null`을 반환하였다. 기기 발성시각이 없는 상태를 미측정으로 처리한 결과이며 반응속도의 개선 수치가 아니다. 관제·글래스별 표출 E2E는 여전히 별도의 기록이 필요하다.

위험 시나리오 GT·검토 완료 구간·측량 좌표는 확보되지 않아 Precision·Recall·F1·FPR·좌표 정확도·비가시권 포착률은 미측정이다. 현재 대시보드의 경보 발행률과 사용자 오경보 반응 비율도 해당 평가표 지표와 구분해야 한다.
